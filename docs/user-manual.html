Section 1

Introduction

Application name

SERVMS — South Eastern Railway Vendor Management System. The application titles itself SERVMS Admin in the sidebar and South Eastern Railway as its sub-title. The login screen is branded “Secure Sign In — Access the Vendor Management System dashboard” and carries the footer “© 2026 Centre for Railway Information Systems (CRIS)”.

Purpose

SERVMS is the single register of record for commercial vendors and contractors operating on South Eastern Railway premises — platforms, stalls, and on-board train services. It replaces separate divisional registers with one role-scoped system that holds the vendor identity record, the contractor commercial record, the physical unit each contract relates to, and every downstream compliance event: police and medical verification, ID card issuance, public credential verification, complaints, inspections, and penalty recovery.

Intended users

SERVMS is an internal, staff-only application. The login page states “Internal Intranet Access Only”. There is no vendor-facing or public-facing self-service portal — vendors and contractors never log in. Accounts belong to railway staff in eight roles across two tiers (HQ and Divisional) plus three operational roles: see Section 6.

The single exception is the public ID card verification page at /verify/<card number>, reached by scanning the QR code on a printed vendor ID card. This page requires no login and is intended for on-platform checking staff, RPF, and the travelling public.

Main objectives

  • Maintain one authoritative vendor and contractor register, scoped so each division sees its own data.
  • Enforce that no vendor ID card is issued without a nominated Card Signing Authority approving it.
  • Make a vendor credential verifiable in seconds from a platform by QR scan.
  • Route every complaint and inspection through a recorded Action Taken Report review chain.
  • Track penalty imposition through to recovery and independent verification of the recovery.
  • Record every create, update, delete, approve, and reject action in a tamper-evident audit trail.

Scope

This manual documents only functionality that is implemented and reachable through the user interface in the current build. Where an API endpoint or database column exists without a corresponding screen, or where a screen element does not do what its label implies, that is stated explicitly and flagged. Nothing in this manual is aspirational.

System overview

Tier 1BrowserReact single-page application
Tier 2APIExpress service under /api, JWT-authenticated
Tier 3DatabaseMySQL, 38 tables

Every screen you use talks only to the API; the API alone reads and writes the database. Permission is checked twice — the browser hides what your role cannot use, and the API independently rejects it. Hiding a button is a convenience, not the security boundary.

Section 2

System Requirements

Browser

SERVMS is a modern single-page application. It requires an evergreen browser released within roughly the last three years — current versions of Google Chrome, Microsoft Edge, Mozilla Firefox, or Safari. It uses ES2020-era JavaScript, CSS Grid, CSS custom properties, and the Fetch API. Internet Explorer is not supported and the application will not render on it.

The following browser features must be enabled or the application will not work correctly:

FeatureUsed forIf disabled
JavaScriptThe entire applicationBlank page

Pop-ups / downloadsCSV, Excel, and PDF exports; ID card PDF downloadExports silently fail to save
Inline PDF viewerDocument preview inside vendor document modalsPreview pane is blank; Download still works

Network

SERVMS is designed for railway intranet access. The browser must be able to reach both the web front end and the API host — these may be different addresses. Uploads accept files up to 20 MB, so a connection that can sustain a 20 MB POST without timing out is required for document-heavy work.

The public verification page (/verify/<card number>) must be reachable from whichever network the scanning device is on. If ID cards are to be verified from personal mobile phones on a platform, that page must be published beyond the intranet.

Display

The application uses a fixed 250 px navigation sidebar alongside a fluid content area, and its widest screens — the Role Management permission matrix (14 rows × 6 permission columns) and the Penalties ledger (8 columns) — are built for desktop. A minimum of 1366 × 768 is recommended; 1920 × 1080 is comfortable. The layout is not optimised for phones or small tablets; tables will require horizontal scrolling.

Access requirements

  • An active SERVMS account, created for you by an administrator. There is no self-registration.
  • Your username and password. Note that the login field is labelled “Employee ID / Username” but the system authenticates on username only — entering your Employee Number will not sign you in unless it happens to be identical to your username.
  • A role that grants view on at least one module. A user with no permissions can sign in but will see an empty sidebar.
Section 3

Login and Authentication

3.1 Reaching the application

  1. Open your browser and go to the SERVMS address supplied by your division administrator.
  2. Any address you enter while signed out redirects to /login. There is no landing or marketing page.
  3. The login screen shows the SERVMS crest, the badge “Internal Intranet Access Only”, and the sign-in card.

3.2 Signing in

  1. In Employee ID / Username, type your username.
  2. In Password, type your password. Use the eye button at the right of the field to reveal what you typed if you need to check it.
  3. Press Secure Login →. The button changes to “Signing in…” while the request is in flight.
  4. On success you land on the Dashboard. On failure a red banner appears above the button.

There is no captcha, no one-time password, and no second factor.

3.3 Password rules

Caution

Because there is no lockout and no complexity rule, the strength of a SERVMS account rests entirely on the password an administrator chooses. Choose a long passphrase when creating accounts, not a six-character minimum.

3.4 Forgotten passwords

Not implemented

The Forgot Password? link on the login screen is not connected to anything. It is an inert anchor that changes the page address to #forgot and does nothing else. There is no self-service password reset.

To recover a forgotten password you must contact an administrator, who follows the assisted reset procedure in Section 7.4. The reset produces a temporary password that the administrator relays to you verbally or in person.

Press Logout at the foot of the left sidebar. This clears the stored token and user record from your browser and returns you to the login screen. Logging out is a browser-side action — the token is discarded, not revoked server-side.

Account status is not checked at sign-in. Setting a user to Inactive through the Toggle action stops nothing — that user can still sign in and use the system normally. Until this is corrected, deactivating an account must not be relied on to remove access. To reliably cut off a departing member of staff, an administrator must change their password to a value they do not know, using the assisted reset in Section 7.4.

6.2 How permission is decided

Permission is a grid of 14 modules × 6 actions. Every role holds one row per module recording whether it may View, Add, Edit, Delete, Approve/Reject, and Export. A missing entry is a denial.

Three rules sit above the grid:

  1. Super Admin HQ bypasses the grid. Every check passes regardless of what the grid records.
  2. Division scoping applies after permission. Divisional Admin, Divisional Sub Admin, and Complaint Cell only ever act on their own division's records; Inspector only on inspections they filed; Dealing Section only on inspections delegated to them.
  3. Some actions name roles directly, bypassing the grid — complaint and inspection type masters, permission-matrix editing, and penalty recovery entry. These are noted where they occur.

6.5 Card Signing Authority

A separate credential from the role, set per user. It is the only thing that permits approving and digitally signing a vendor ID card. To be eligible a user must satisfy both conditions:

  • Role is HQ Admin, HQ Sub Admin, Divisional Admin, or Divisional Sub Admin, and
  • Designation Grade is JS or SS.

An eligible user must additionally be given an Authority Designation — the wording printed on issued cards, for example “Divisional Administrator, Kharagpur Division”. A signature image should also be uploaded, or cards will be produced without a visible signature.

7.3 Editing and deleting users

Not implemented

There is no way to edit or delete a user through the interface. The listing offers only Toggle, Reset Password, and Transfer. Once a user is created, their name, Employee Number, username, designation, grade, email, mobile, signing authority, station, and signature can never be changed on screen. Role and division can be changed only by raising and approving a Transfer request. Correcting a typo in a name requires a database change.

Toggle (activate / deactivate)

Press Toggle to flip a user between Active and Inactive. There is no confirmation prompt and the change is immediate. The button is hidden for Admin-tier accounts unless you are Super Admin HQ.

Known gap

Setting a user Inactive does not stop them signing in — see Section 3.7. Toggle changes the badge in the Status column and nothing else.

7.4 Password reset (assisted)

SERVMS uses a two-person reset: one administrator raises the request, another approves it. Both parties need User Management permissions — raising needs Edit, approving needs Approve/Reject.

Step 1RaiseAdministrator submits with an optional reason
Step 2NotifyEmail sent to the HQ admin mailbox
Step 3QueueAppears under Pending Requests
Step 4DecideApprove or Reject
Step 5RelayTemporary password shown once
  1. Find the user and press Reset Password.
  2. Optionally record a reason, then press Submit Request. A confirmation states the request has been routed for review.
  3. An approver opens Pending Requests and selects the Password Resets tab, which shows User, Requested By, Reason, and Date.
  4. Press Approve. A green banner displays a freshly generated temporary password of roughly eight characters.
  5. Copy it now. It is shown once, is never emailed, and cannot be retrieved afterwards. If it is lost, raise a fresh request.
  6. Relay it to the user securely. Pressing Reject instead closes the request and leaves the password untouched.
Known gap

An approved reset marks the account as holding a temporary password, but there is no screen on which a user can change their own password. The user signs in with the temporary password and is never prompted to replace it — the temporary password simply becomes their permanent one. To change it again, another assisted reset must be raised.

7.5 Transfer requests

The only mechanism for changing a user's division or role after creation. Same two-person pattern as password reset.

  1. Press Transfer on the user's row. Current Division and Current Role are shown read-only.
  2. Choose a New Division, a New Role, or both. Leaving both as “No change” is rejected with “Select a new division and/or role to request a transfer.”
  3. Optionally record a reason and press Submit Request.
  4. An approver opens Pending Requests → Transfers, which shows the user, the proposed change as from → to, who requested it, and when.
  5. Press Approve to apply the change to the account, or Reject to close the request unchanged.

The Transfer button is hidden for Admin-tier accounts unless you are Super Admin HQ.

Note

An approved transfer changes the stored account, but the affected user keeps their existing session with the old role and division until they sign out and back in. Ask them to sign out and in again after a transfer is approved.

Caution

A newly created role starts with no permissions at all. It must be selected in the list and given permissions in the matrix before anyone assigned to it can do anything. Note also that the role name you type is stored raw — only the eight built-in roles have friendly display names, so a custom role will show its raw name wherever roles are listed.

8.3 Editing a role

Press the pencil icon on a role's row. Only two properties can be changed: Description and Status (Active / Inactive). The role name cannot be changed after creation.

8.4 Deleting a role

Press the bin icon. A browser confirmation asks “Delete role ‘…’? This cannot be undone.” Only Super Admin HQ holds Delete on Role Management, so for every other role the button either does not appear or the action is refused. If the role is in use the server refuses and the reason appears in a red banner.

8.5 The permission matrix

Selecting any row in the role list loads its permission matrix below the table, headed Permission Matrix — <role>. Fourteen module rows against six checkbox columns: View, Add / Create, Edit / Update, Delete, Approve / Reject, Export Data.

  1. Select the role whose permissions you want to change.
  2. Tick or untick the boxes. Use Select All above the table to set or clear every box at once.
  3. Press Save Changes. The button reads “Saved ✓” on success.

Only Super Admin HQ, HQ Admin, and Divisional Admin can save. For every other role the checkboxes render disabled and the Save button is hidden.

Misleading control

The button labelled Reset to Default does not reset anything to a default. It re-reads the currently saved permissions from the server, discarding unsaved ticks on screen. Read it as “Discard my changes”. There is no way to restore a role's original shipped permissions once they have been saved over.

Caution

Changes take effect the moment they are saved, for every user holding that role, without them signing out. Removing View on a module removes it from their sidebar mid-session. Take particular care with Super Admin HQ: its permissions are ignored in favour of an unconditional bypass, so editing that row has no effect and cannot lock anyone out — but editing HQ Admin or Divisional Admin can.

Four statistic cards — Total Reports Generated, Total Exports, Modules Reported On, Most Used Report — followed by four navigation buttons, two activity panels (Recent Exports and Most Used Reports), and module summary blocks for Vendor Management, Contractor Database, Complaints & Grievances, and Penalties & Fines.

Note

17.2 Report Builder

Requires Add on Reports. Eight modules can be reported on: Vendors, Contractors, Units, Penalties, ID Cards, Users, Complaints, and Inspections.

  1. Select Module. The available fields load for that module.
  2. Choose fields. Tick the columns to include.
  3. Add filters. Press Add filter for each condition. The operators offered depend on the field type — date and number fields offer ranges and comparisons; text fields offer contains-style matching; enumerated fields offer set membership.
  4. Set sorting. Choose a field and Asc or Desc.
  5. Group and aggregate if you want totals rather than rows.
  6. Preview. Returns the first 20 rows so you can check the shape before exporting.
  7. Export as CSV or Excel, or Save as a reusable template.

17.3 Saving templates

Saving captures the module, fields, filters, sort, and grouping under a Name and optional Description. Mark a template Shared to make it available to colleagues; leave it unshared to keep it private.

17.4 Saved Reports

Columns: Name, Module, Created By, Shared, Usage, Last Used, Actions. Actions: Run (opens the builder pre-loaded), toggle sharing, and delete. Usage counts and last-used dates are maintained automatically.

17.5 Export History

A read-only log at /reports/exports with columns Module, Report, Format, Rows, Exported By, and Date. Every builder export is recorded here, giving a complete record of who extracted what data and when.

Note

Only Report Builder exports appear here. The per-module exports — the Vendor, Penalty, User, Complaint, Inspection, and Audit Log downloads — are not recorded in Export History.

Section 20

Audit Logs

Address /audit-logs · Available to Super Admin HQ, HQ Admin, Divisional Admin

20.1 What is recorded

Every log entry captures: the user, their role, the action, the module, the record identifier, the data before the change, the data after the change, free-text details, the IP address, the browser user-agent, and the timestamp. Passwords are stripped before anything is written.

Actions are recorded across User Management, Roles, Vendors, Contractors, Units, Trains, Clusters, ID Cards, Complaints, Complaint Types, Inspections, Inspection Types, Penalties, Renewals, Reports, Dropdowns, Imports, Exports, Assignments, and ATR decisions.

20.2 Filters

Module and Action are always visible. Advanced Filters adds Record ID, User ID, and a From / To date range. Twenty entries per page.

20.3 Reading an entry

Each row summarises one action. Expanding a row reveals the before and after data, so you can see exactly which values changed.

20.4 Exporting

Requires Export on Audit Logs. Export Excel produces a CSV file; Export PDF produces a formatted PDF. Both apply your current filters.

Known gap

The Action filter offers Login, Logout, Download, Print, Password Reset, Recover, Renew, and Issue, but no part of the system writes entries with these actions. In particular, sign-in and sign-out are not audited at all. Filtering by Login always returns an empty result. The only record of a sign-in anywhere in SERVMS is the “Last Login” column in User Management, which holds the most recent time only.

If a sign-in audit trail is a compliance requirement for your division, it is not currently satisfied.

Section 23

Security Guidelines

23.1 Your password

  • Choose a long passphrase. The six-character minimum is a floor, not a target — there is no complexity rule and no lockout to fall back on.
  • Never reuse your SERVMS password on another system.
  • Never share it. There is no legitimate reason for anyone, including an administrator, to ask for it — an administrator who needs to help you can reset it instead.
  • Change it if you suspect it is known. Because there is no self-service change, this means asking for an assisted reset.
  • Administrators: relay temporary passwords in person or by phone, never by email or chat.

23.2 Sessions

  • Press Logout when you leave your desk. The session lasts 12 hours and does not time out on idle.
  • Lock your workstation as well — the session lives in the browser and survives closing the tab.
  • Never sign in on a shared or public machine. If you must, use a private window and sign out explicitly.

23.3 Accounts and access

  • Never work under someone else's account. Every action is attributed to the signed-in user, so borrowing an account falsifies the audit trail.
  • Grant the least permission the job needs. Approve/Reject and Export are the two most consequential.
  • Review the user list periodically for accounts whose Last Login is “Never” or long past.
  • To remove access from a departing member of staff, have their password reset to a value they do not know. Deactivating alone does not block sign-in.

23.4 Documents

  • Upload only documents that belong on the record you are attaching them to.
  • Treat every document address as public. Anyone with the link can open the file without signing in — never forward a link to someone who should not see the document.
  • Download identity documents only when there is an operational need, and delete local copies afterwards.

23.5 ID cards and QR codes

  • The QR on a printed card contains the vendor's full Aadhaar number and home address in plain text. Anyone who scans it obtains both.
  • Card PDFs are the same — treat a downloaded card as an identity document.
  • Never approve a card for a vendor whose verifications you have not checked. Your name and designation are printed on it and encoded in the QR.
  • Card Signing Authority is a personal credential. Never let a colleague approve cards from your session.

23.6 Reporting a concern

Report a suspected compromise, an unexpected permission, or a record you should not be able to see to your division administrator immediately, and to the CRIS support desk. Include the exact wording of any message, the screen, and the time — the audit trail can then be matched against your report.

Section 24

Frequently Asked Questions

I have forgotten my password. How do I reset it myself?

You cannot. The Forgot Password link on the login screen is not connected to anything. Contact an administrator, who raises a reset request for a second administrator to approve; you are then given a temporary password (Section 7.4).

Why does my colleague see more menu items than I do?

The sidebar shows only modules your role can view. Different roles see different menus.

I typed my Employee Number and could not sign in.

The field is labelled “Employee ID / Username” but only the username works. Ask an administrator for your username — it is shown next to your Employee ID in User Management.

How do I correct a spelling mistake in a vendor's name?

You cannot through the interface — there is no edit-vendor screen. Only status, the two verifications, and unit or contractor transfers can be changed after onboarding. A name correction requires a database change through the CRIS support desk. Check Step 1 of the wizard carefully before submitting.

How do I change a user's name, email, or mobile number?

You cannot. There is no edit-user screen. Role and division can be changed through a Transfer request; nothing else can be changed on screen.

Why can I not delete anything?

Only Super Admin HQ holds Delete on any module. This is deliberate — records referenced by complaints, inspections, penalties, and the audit trail should be deactivated rather than erased. Use status changes and deactivation instead.

I set a user to Inactive but they can still sign in.

Correct — account status is not checked at sign-in. To reliably remove access, have their password reset to a value they do not know.

Why can I not approve an ID card even though I am an Admin?

Card approval needs the Card Signing Authority credential, which is separate from your role. It requires an HQ or Divisional Admin or Sub Admin role and a JS or SS designation grade, and it must be granted on the user record.

The vendor has no ID card option and I cannot request one.

Requesting requires Add on ID Card Management. If the request is refused with “no valid-till date on file”, complete the vendor's police or medical verification dates first — the card's expiry is copied from one of them.

What happens to an existing card if I re-issue?

It returns to Pending Approval and the previous approval is cleared. The vendor has no valid card until a signing authority approves again. Do not re-issue unless a fresh card is genuinely needed.

Someone scanned a card and the page said NOT ISSUED.

The card exists but is not in the Approved state — it is pending, was rejected, or has been re-issued and is awaiting approval. Check the card in ID Card / QR Management.

Can vendors or contractors log in?

No. SERVMS is staff-only. The only page a non-staff member can reach is the public ID card verification page.

Why does the Dashboard show a figure the list does not reproduce?

The three licence-fee sub-groups link to a screen with no licence-fee filter, so the list is division-scoped only. Trust the Dashboard figure.

Why is my Excel export actually a CSV file?

Two buttons labelled Excel produce CSV: Vendor Management and Audit Logs. Both open correctly in Excel. Complaints, Inspections, and the Report Builder produce genuine .xlsx workbooks.

My export seems to be missing rows.

Vendor and Penalty exports are capped at 2,000 rows with no warning. Use the Report Builder for larger extracts.

Can I bulk-upload vendors or contractors?

No. Stations are the only master that can be imported, plus RailMadad complaints. Everything else is entered individually.

Will SERVMS email or text me when something needs attention?

No. Despite the preference switches in the Notification Centre, no email, SMS, or push notification is ever sent. Check the Notification Centre inside the application.

Why did my notification badge reset on a different computer?

Read state is stored in your browser, not on the server, so it does not follow you between machines or browsers.

Where are the Settings and Help pages?

Neither exists. Placeholder files are present in the codebase but are not reachable from anywhere in the application.

Can I see who viewed a record?

No. The audit trail records changes — create, update, delete, approve, reject, transfer — not reads. Sign-ins are not recorded either.

Why does “Record not found” appear for a record I know exists?

It is outside your division. The message is deliberately identical for “does not exist” and “exists but is not yours”, so scope cannot be probed. Ask a colleague with wider scope.

I changed a role's permissions but the affected user still sees the old menu.

Module permissions refresh as the application is used, so the change should appear within moments. Role and division changes from a Transfer, however, require the user to sign out and in again.
