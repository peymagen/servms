Headline assessment

SERVMS is a substantially complete system. Its core — the permission model, division scoping, the ID card issue-and-sign workflow, both Action Taken Report chains, and the penalty money trail — is implemented thoroughly and defended consistently at both the browser and the server. The audit trail captures before-and-after values across every write path.

The gaps cluster in three places rather than spreading evenly: record maintenance after creation (no edit screen for vendors or users), outbound communication (no channel exists behind the notification preferences), and account lifecycle (deactivation does not deactivate). The first two are absences; the third is a correctness defect and the single most consequential finding in this report.

Section 4

Partially Implemented

F–01Vendor Renewals is not permission-checkedHigh
What exists
The full renewal workflow — create, list, approve, reject — works, and approval correctly pushes the new expiry onto the vendor record and reactivates them.
What is absent
The renewal router applies authentication only. No endpoint carries a permission guard, so any authenticated user — Inspector, Dealing Section, Complaint Cell — can create, approve, and reject renewals. The screen's own Approve and Reject buttons are not permission-gated either. Every other module in SERVMS guards both layers.
Consequence
An expired vendor can be returned to Active service by any signed-in user. This is the widest privilege gap in the system.
Remedy
Add requirePermission("vendor_management", …) to each renewal route — view on the reads, create on the POST, approve/reject on the PATCH — and gate the screen's buttons to match.
Documented
User Manual §6.4 and §13, both as prominent warnings.
F–02No edit or delete screen for vendorsMedium
What exists
Working update and delete endpoints, correctly guarded, with matching client API definitions already written.
What is absent
No screen invokes either. The client hooks useEditVendorMutation and useDeleteVendorMutation are defined and never referenced. Only status, the two verifications, and unit or contractor transfers can be changed after onboarding.
Consequence
Twelve captured fields — name, father's name, date of birth, Aadhaar, mobile, address, blood group, vendor type, photograph, signature, and both validity dates — are permanent from the moment the wizard is submitted. A misspelled name needs a database change.
Remedy
Add an edit view reusing the wizard's field definitions. The endpoint and its validation already exist, so this is UI work only.
Documented
User Manual §11.4; Training Manual §7.1 as the “golden rule”.
F–03No edit, delete, or approval screen for usersMedium
What exists
Working endpoints for full update, partial update, delete, approve, and reject — all correctly guarded, including the Admin-tier check.
What is absent
User Management offers only Toggle, Reset Password, and Transfer. No client API definition exists for edit, delete, approve, or reject, so no screen could call them. The pending_approval user status has no interface at all.
Consequence
Once created, a user's name, Employee Number, username, HRMS ID, designation, grade, email, mobile, station, signing authority, and signature are permanent. Card Signing Authority in particular can never be revoked through the interface.
Remedy
Add an edit dialog mirroring Add New User, plus an approval queue for pending accounts. Endpoints and validation already exist.
Documented
User Manual §7.3.
F–04Assignment to a named individual has no controlMedium
What exists
Both the complaint and inspection assignment endpoints accept an assignee, validate it, store it, and join it back for display. The assignment history and the detail views are ready to show an assignee name.
What is absent
Both assignment dialogs offer a target unit and remarks only. No control sets the assignee, so it is always empty.
Consequence
Work can be routed to units but never to people. The Dealing Section's assignee-scoped visibility therefore rests on unit assignment alone, and personal accountability for an assigned case is not recorded.
Remedy
Add an optional assignee picker to both dialogs, populated from users in the target unit's division.
Documented
User Manual §14.6 and §15.6.
F–05Contractor edit form is narrower than registrationMedium
What exists
Nine fields are editable: contact, mobile, email, licence number and validity, registration fee, award date, tenure, and contract value.
What is absent
Company name, PAN, GSTIN, registered address, and division are captured at registration and appear on no edit form — even though the update endpoint accepts and validates all five.
Consequence
A statutory identifier entered incorrectly at registration cannot be corrected. Division in particular cannot be changed, so a contractor registered against the wrong division stays there.
Remedy
Extend the edit form to the fields the endpoint already accepts.
Documented
User Manual §10.3.
F–06Clusters cannot be editedLow
What exists
A working cluster update endpoint and a defined useEditClusterMutation hook.
What is absent
The Clusters tab renders a Remove action only. The hook is never referenced. Units, Stations, and Trains all have edit actions.
Consequence
Changing a cluster's name, type, or membership requires removing and recreating it, breaking any unit that references it.
Remedy
Add an edit action to the Clusters tab. The endpoint and hook already exist.
Documented
User Manual §9.4.

F–07The Admin Module permission governs nothing reachableMedium
What exists
admin_module is one of the 14 modules in the permission matrix, is granted to Super Admin HQ and HQ Admin, and guards four working dropdown-administration endpoints.
What is absent
No screen calls any of them. The client's dropdown API is read-only in practice — the only category read anywhere is contract_category, on the unit form. Complaint and inspection type masters have their own screens, guarded by role name rather than by this permission.
Consequence
A row in the permission matrix that changes nothing, and a managed-dropdown facility that can only be administered by direct API call. Contract categories in particular cannot be maintained by any user.
Remedy
Either add a dropdown administration screen behind this permission, or remove admin_module from the matrix so it does not imply a capability that is unreachable.
Documented
User Manual §5.2; Training Manual §7.4.
F–08Temporary passwords can never be replaced by their ownerHigh
What exists
An approved reset generates a temporary password, stores its hash, and flags the account. The change-password endpoint exists, validates a current and new password, and clears the flag on success.
What is absent
No screen calls it and no client hook is defined. The temporary-password flag is set and never read: nothing prompts the user, and nothing blocks normal use.
Consequence
A system-generated temporary password, transcribed by hand from a banner and relayed verbally, becomes the account's permanent credential. Changing it again requires a fresh two-person reset. Over time, a growing share of accounts are secured by short machine-generated strings that have been spoken aloud.
Remedy
Add a change-password screen, and force it on next sign-in whenever the temporary flag is set. The endpoint and validation already exist.
Documented
User Manual §7.4 and §3.4; Training Manual EX–07 makes trainees discover it deliberately.
Section 6

Present in the UI, Not Properly Connected

Visible controls that do not do what a user would reasonably expect.

F–09The global search field is decorativeMedium
Where
Application top bar, on every signed-in screen.
Behaviour
Rendered with a placeholder reading “Search across SERVMS…” and no value binding, no change handler, and no submit handler. It accepts typing and does nothing with it.
Consequence
The most prominent control in the frame is inert. Users type into it and conclude the system is broken or slow. No cross-module search exists anywhere.
Remedy
Implement it, or remove it. Leaving a visibly inert search field in the frame of every screen actively misleads.
Documented
User Manual §5.1 and §22.7; Training Manual EX–24 step 1.
F–10“Forgot Password?” is a dead anchorMedium
Where
Login screen, beside the password field.
Behaviour
An anchor targeting #forgot. No such element or route exists. It changes the address fragment and nothing else.
Consequence
A locked-out user presses the one control that appears to help them and gets no feedback at all. Support load falls on administrators with no prompt telling the user to contact one.
Remedy
Replace with guidance text naming the assisted-reset procedure, or build the flow. The email service and templates already exist.
Documented
User Manual §3.4; Training Manual EX–24 step 2.
F–11Notification preferences are saved but have no channelMedium
Where
Notification Centre, lower half.
Behaviour
Email Alerts, SMS Alerts, Push Notifications, three per-category channel matrices, and a digest frequency are all persisted — to browser storage. Nothing on the server reads them, and no email, SMS, or push channel exists for any of these events. The only outbound message SERVMS ever sends is the password-reset notice to a fixed HQ mailbox, which these settings do not control.
Consequence
The panel represents a complete alerting subsystem that does not exist. Its presence is worse than its absence: a user who enables Email Alerts for Financial Audits reasonably stops checking the Dashboard.
Remedy
Hide the panel until a channel exists, or label it clearly as forthcoming. Then implement server-side delivery driven by the same rules the in-app feed already computes.
Documented
User Manual §19.4; Training Manual EX–24 step 6 and the non-negotiable assessment items.
F–12“Reset to Default” does not reset to a defaultLow
Where
Role Management, above the permission matrix.
Behaviour
Re-reads the currently saved permissions from the server, discarding unsaved changes on screen. No default matrix is stored anywhere, so none can be restored.
Consequence
An administrator who has just saved a damaging change presses this button expecting recovery and gets confirmation of the damage instead. There is no undo for a permission save.
Remedy
Rename to “Discard Changes”. Separately, consider seeding a stored default matrix so a genuine reset becomes possible.
Documented
User Manual §8.5; Training Manual EX–08 and §11.1.
F–13Two unreachable placeholder screensLow
Where
SettingsPage.tsx and HelpCenterPage.tsx.
Behaviour
Both are complete components with a heading and one line of placeholder text. Neither is registered as a route and neither has a menu entry, so neither can be opened by any means. Both addresses fall through to the Dashboard.
Consequence
Dead code implying a settings and help capability that does not exist. SERVMS has no settings screen; the only user-adjustable preferences anywhere are the inert notification ones from F–11.
Remedy
Delete both, or complete and route them.
Documented
User Manual §5.3; Training Manual EX–24 step 9.
F–14“Export Summary” downloads raw JSONLow
Where
Reports hub, top right.
Behaviour
Serialises the four on-screen metric objects and downloads them as servms-report-summary.json.
Consequence
Beside a Report Builder producing CSV and XLSX, a button labelled “Export Summary” that yields a developer-oriented data file is misleading. It cannot be opened by its likely audience.
Remedy

Section 8

Inconsistencies Between Layers

F–15Account status is not checked at sign-inHigh
Layers
Database defines four statuses — active, inactive, suspended, pending_approval. The UI exposes a Toggle action and renders the status prominently. The authentication path reads none of it.
Behaviour
The login lookup selects the user by username and verifies the password. It does not filter or test users_status at any point. A user set to Inactive, Suspended, or Pending Approval signs in normally and operates with full role permissions.
Consequence
Deactivation is presentational. The one control an administrator would use to remove a departing member of staff's access does not remove it, while displaying a badge that says it has. This is the most consequential defect in the system: it is silent, it looks like it worked, and the failure only becomes visible if someone tests it.
Remedy
Reject sign-in for any status other than active, with a distinct message. Consider also rejecting requests whose token belongs to a since-deactivated account.
Documented
User Manual §3.7, §7.3, §22.7, §23.3, and the FAQ; Training Manual EX–24 step 5 and a non-negotiable assessment item.
F–16Audit filter offers eight actions that are never writtenHigh
Layers
The audit service defines 22 action types. The Audit Logs screen offers 17 of them as filters. Only 14 are ever written by a controller.
Behaviour
LOGIN, LOGOUT, DOWNLOAD, PRINT, PASSWORD_RESET, RECOVER, RENEW, and ISSUE appear in the filter and are written nowhere. Most seriously, the login controller updates the last-login timestamp and issues a token without writing any audit entry.
Consequence
Sign-ins and sign-outs are not recorded anywhere. The only trace of a sign-in is the “Last Login” column, which holds one timestamp and is overwritten each time. There is no way to establish who accessed the system, when, or from where — and no way to detect use of a compromised account. An auditor filtering for Login receives an empty result that reads as “no sign-ins occurred”.
Remedy
Write a LOGIN entry on success (and on failure, which would also give the missing basis for lockout), a LOGOUT entry on sign-out, and PASSWORD_RESET on reset approval. Remove filter options for actions that remain unwritten.
Documented
User Manual §20.4 as a prominent gap; Training Manual EX–23 step 12 makes trainees observe it.
F–17Sub Admins are entitled to manage type masters but cannot see the buttonsMedium
Layers
Server: complaint and inspection type management is gated on an explicit role list — HQ Admin, Divisional Admin, HQ Sub Admin, Divisional Sub Admin. UI: the Complaints screen gates its button on admin_module: create or complaint_management: approve_reject; the Inspections screen on inspection_management: approve_reject.
Behaviour
Neither Sub Admin role holds any of those permissions, so neither sees either button — despite being explicitly permitted by the server.
Consequence
A documented entitlement is unreachable for two of the eight roles. Type-master maintenance falls entirely to the Admin tier, contrary to the intended delegation. This also matters operationally: RailMadad imports create complaint types automatically, and curating them is exactly the kind of task a Sub Admin should own.
Remedy
Gate both buttons on the same role list the server uses.
Documented
User Manual §14.8 and §15.9; Training Manual §4.3, §4.5, and EX–24 step 10.
F–18Client API base address does not match the server portMedium
Layers
client/.env sets the API base to port 5000. server/.env.example and the README both specify port 4000, and the README explicitly notes that 4000 was chosen to avoid a conflict on macOS. The compiled default in the client source points at a production host.
Consequence
A developer following the README gets a client that cannot reach its API, with network errors and no explanatory message. Three sources disagree about a single value.
Remedy
Align client/.env with the documented port and remove the production host as a compiled-in fallback.
F–19README describes a setup that does not existMedium
Layers
The README instructs the reader to run server/database/setup.sql, describes a 16-table schema, and lists superadmin as the Super Admin username. The repository actually contains server/db_schema.sql with 38 tables and a seed.ts script, and the seeded Super Admin username is superadminhq.
Consequence
The published setup path fails at the first command. The documented sign-in credential is wrong. A new starter cannot get the system running from the README alone.
Remedy
Rewrite the database setup section against the current schema file and seed script, and correct the credential table.
F–20Uploaded documents are publicly readableMedium
Layers
Every upload — Aadhaar scans, medical certificates, police verification reports, penalty recovery receipts, generated ID card PDFs — is written to a directory served as unauthenticated static content.
Behaviour
Anyone holding a document address can open it without signing in. Names include a timestamp so they are not trivially guessable, but they are also not protected, and the addresses appear in the browser and in shareable links.
Consequence
The permission matrix and division scoping govern who can find a document, not who can read one. A link forwarded outside the intended audience discloses the file. Vendor identity documents and generated ID cards are the most sensitive material in the system.
Remedy
Serve uploads through an authenticated route that checks the requester's permission and division scope against the owning record.
Documented
User Manual §21.4 and §23.4.
F–21QR payload carries full Aadhaar and address in plain textMedium
Layers
The QR text encodes the vendor's name and address, full Aadhaar number, both verification validity dates, unit, vendor type, contractor, card validity, issuing authority, a verification link, and a status-sheet link. The public verification page independently displays the full Aadhaar and address to anyone who opens it.
Behaviour
Scanning a printed card with any QR reader yields the full payload without contacting SERVMS at all. Format 1 masks the Aadhaar in its printed body — but the QR beside it does not.
Consequence
A printed vendor ID card is a self-contained disclosure of that vendor's Aadhaar number and home address. The masking on Format 1 gives a false impression of protection.
Remedy
Reduce the QR payload to the card number and the verification link, and let the authenticated-or-limited verification page decide what to reveal. Mask the Aadhaar on the public page.
Documented
User Manual §12.6, §12.7, §23.5; Training Manual EX–18 and a non-negotiable assessment item.
F–22Two “Excel” buttons produce CSVLow
Behaviour
Vendor Management's Export to Excel and Audit Logs' Export Excel both build CSV. Complaints, Inspections, and the Report Builder produce genuine .xlsx workbooks.
Consequence
Both open correctly in Excel, so the impact is cosmetic — but inconsistent labelling across a single application undermines confidence in the rest of it.
Remedy
Relabel, or produce XLSX using the workbook writer already present.
Documented
User Manual §18.4.
F–23Vendor and Penalty exports truncate silently at 2,000 rowsLow
Behaviour
Both exports request a fixed limit of 2,000 rows. If the filtered set is larger, the file simply stops. No warning, no indication in the file, no row count shown.
Consequence
An incomplete extract that looks complete. A division with more than 2,000 vendors would produce a truncated compliance report with nothing to signal it.
Remedy
Paginate through the full set, or warn when the total exceeds the cap.
Documented
User Manual §18.4 and the FAQ; Training Manual §8.3.
F–24Notification read state is per-browser, not per-userLow
Behaviour
Read notification identifiers are kept in browser storage. Nothing is sent to the server.
Consequence
The unread badge differs between a user's own machines and resets when browser data is cleared. Two people sharing a workstation share each other's read state.
Remedy
Persist read state per user on the server, or accept and document the limitation as a deliberate simplification.
Documented
User Manual §19.3.
F–25Dashboard licence-fee figures link to a screen that cannot reproduce themLow
Behaviour
Three Pending Action sub-groups — licence fee due within 7 days, within 14 days, and overdue — navigate to Location & Unit Management with a division filter only. That screen has no licence-fee filter.
Consequence
The figure clicked and the list arrived at do not correspond, with nothing on screen to explain why. The user cannot act on the number they were shown.
Remedy
Add a licence-fee-due filter to the Units tab and thread it through the link.
Documented
User Manual §4.4; Training Manual EX–03.
F–26Contractor status enum is inconsistent between create and change-statusLow
Behaviour
Create and update validation accept active, pending_approval, suspended, and expired. The change-status action additionally accepts blacklisted, and the client type declares all five. Blacklisting is therefore reachable only through the dedicated status action — which is deliberate, and mirrors the vendor module.
Consequence
Correct behaviour, but not evident from the type definitions alone. Worth an explicit note in the schema.
Remedy
Document the intent in the validation file, as the vendor module already does.
F–27Identity fields validated on length onlyLow
Behaviour
Aadhaar is checked for exactly 12 characters — not that they are digits. PAN is checked for exactly 10 characters, GSTIN for exactly 15, neither against its known format. Mobile numbers are trimmed and otherwise unchecked, on both users and vendors, despite being mandatory on both forms.
Consequence
Transcription errors pass validation and reach the database. Since vendors have no edit screen (F–02), a mistyped Aadhaar is permanent — and it is printed on the ID card and encoded in the QR.
Remedy
Apply format patterns to Aadhaar, PAN, GSTIN, and mobile. Low effort, and it compounds with F–02.
F–28Record codes generated from a random number rather than a sequenceLow
Behaviour
Vendor codes are V-2026- plus a random four-digit number; complaint codes and penalty codes follow the same pattern. Contractor codes and inspection numbers, by contrast, use proper counters — CON-001 and INSP-2026-000001.
Consequence
Only 9,000 distinct vendor codes exist per year. Collisions become likely well before that — at around 100 vendors the chance of a duplicate is roughly one in two. A collision surfaces as an opaque database error at the end of the wizard, and the vendor year prefix is hard-coded to 2026.
Remedy
Use the same counter approach as inspection numbers for vendors, complaints, and penalties, and derive the year from the current date.

11.3 Deliberately excluded

No credential, secret, key, connection string, or internal address appears in any of the three documents. Security findings are stated in terms of what a user must do differently, not in terms of how to exploit them. The two authentication findings (F–15, F–16) are documented because staff must know that deactivation does not remove access and that sign-ins leave no trail — withholding either would leave readers relying on a control that does not work.

11.4 Documentation review triggers

Any of the following changes invalidates part of the manuals and should trigger a revision:

  • A change to the seeded permission matrix — User Manual §6.3 states it exactly.
  • A new role, module, or permission action.
  • Remediation of any finding in Section 10 — each is documented as a current limitation and several appear in the training assessment.
  • A new screen, or a screen removed from the navigation.
  • A change to any workflow's state machine — complaint, inspection, penalty, ID card, or renewal.
  • A change to upload types or size limits.
